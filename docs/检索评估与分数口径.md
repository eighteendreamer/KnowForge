# 检索评估与分数口径

> 面向：调参、验收、以及要把 KnowForge 接进 RAG 并自行设阈值的调用方。
> 本文所有数字都来自本地单节点部署的真实模型调用与真实语料（`docs-spider/pdfs`，31 篇 ready / 2494 分块），不是估算。
> 复现命令见第 6 节；口径变更必须同步改 `scripts/build_eval_dataset.py` 与本文件。

## 1. 评估集怎么来的

- **Query 来源**：正文小节标题里的"问句式标题"（含 `？/?`）与"疑问式标题"（什么是/如何/怎么/为什么/有哪些/有哪几/哪些场景/区别/原理/流程/机制/优势/缺点/是否/怎样/怎么办/注意事项）。每条 Query 记录 `query_origin`，便于复核来源分布。
- **分层与覆盖**：`data/evaluation/frozen-<版本>.jsonl` 输出 `frozen_coverage`，按 文件类型 / 内容形态（表格、代码、图片、跨页、HTML）/ 难度 / 分类 计数；规模要求 300~500 条。
- **不泄漏**：按 `doc_id` 摘要取模把整篇文档划进调优集或冻结集（同一篇文档不可能同时出现在两侧），禁止用同一批 Query 调完参再拿去报成绩。
- **对照集**：5 条语料外主题（打印机脱机队列、烘焙水合比、轮胎动平衡…）。构建时用 `fuzzy_search` 实际探测，一旦命中就报错要求换题，保证"知识库未覆盖"这条路径可测。

## 2. 相关性标注口径（为什么以前 Precision@5 上不去）

旧实现只在**同一篇文档内**按规则打标签，于是"检索到了另一篇文档里的正确答案"被当成错，Precision@5 被结构性压到 0.3 左右（实测见 `data/acceptance/evaluation-shadow.json`：Recall@5 0.9071 / MRR 0.9939 / NDCG@10 0.9477 同时 Precision@5 只有 0.3106）。

现口径改为**池化标注（pooled judging，IR 领域对未判分偏差的标准处理）**：

1. 每条 Query 先用 semantic / keyword / fuzzy 各取 top-25，并集成候选池（实测并集最多 62 条）。评估用的 top-5 必然落在池内，因此不存在"判对了但没标注"。
2. 池内每条候选按写死的 rubric 由配置好的 LLM（`temperature=0`，JSON 模式）打 0/1/2 分；rubric 的 SHA-256 记在构建报告里（`rubric_sha256`），换 rubric 就是换评估集版本。
   - `2` 直接回答：只读这一段就能拿到答案要点
   - `1` 部分覆盖或必需背景
   - `0` 不相关；**未出现在标签里同样按 0 计**
3. 自动 Query 的质量闸门：如果小节自己的分块都没被判为 `2`，说明这条标题不像个问题，整条 Query 丢弃并计数（`dropped_queries_without_seed_grade_2`）。
4. 人工可复核：`data/evaluation/review-frozen-<版本>.csv` 每行一条 (query, chunk_id, model_grade)，在 `human_grade` 列填数字后另存为 `overrides-<版本>.csv` 即可覆盖，覆盖条数记进报告。列名契约由 `backend/tests/test_eval_dataset.py::test_review_file_round_trips_human_grades` 锁住。
5. 缓存 `pool-<版本>.jsonl` / `grades-<版本>.jsonl` 的 key 里带知识库 revision，语料一变就强制重新池化，不会拿旧池子评新库。

## 3. 指标定义与完成标准

| 指标 | 计算方式 | 阈值 |
|---|---|---|
| Recall@10 | 每条 Query：Top10 命中的已标注相关分块数 ÷ 该 Query 全部相关分块数，再取均值 | ≥ 0.85（切换门） |
| Recall@5 | 同上，截断深度取 5 | 观测项，见 3.1 |
| MRR | 第一个相关结果排名的倒数均值 | ≥ 0.75 |
| NDCG@10 | 用 0/1/2 等级算的归一化折损累计增益 | ≥ 0.80 |
| Precision@5 | Top5 中相关（等级 > 0）条数 ÷ 5 | ≥ 0.80 |
| hit@5 / missed_relevant_at_5 | 报告里逐变体输出，用于区分"排序差"和"库里根本没有" | 观测项 |
| 对照误召回 | 语料外 Query 在 Top5 拿到结果的条数 | 观测项，单独统计，不进 Recall 分母 |

门指标只此一份定义：`backend/app/schemas/system.py` 的 `EVALUATION_TARGETS`，服务端（`routes/system.py`）与 `scripts/acceptance_evaluation.py` 都导入它；`test_evaluation_targets.py` 钉住"每个门键都是 `EvaluationMetrics` 的字段"，防止两处各自漂移或某项被静默漏判。

分块级指标在"相邻分块合并展示"之前计算；不足 K 条的位置按未命中处理。

### 3.1 Recall@5 ≥ 0.85 在池化标注下不可达（已实测，处理办法已拍板）

池化标注只给"被检索到的候选"打过分，未打分一律按不相关计（方案 8.1.2/8.1.4 的口径）。冻结集 279 条可评分 Query 的相关分块数为 min 1 / 中位 5 / p95 16 / max 22，均值 6.48。于是每条 Query 的 Recall@5 有一个人人不同的上界 `min(5, R) / R`：

| 口径 | 完美排序下的上界 | 对 0.85 这条门 |
|---|---|---|
| Recall@5 | **0.7792** | 不可达，且 137/279 条 Query 单条上界就低于 0.85 |
| Recall@10 | 0.9469 | 可达 |

结论：`Recall@5 ≥ 0.85` 与"未标注按不相关计 + 每条 Query 平均 6.5 个相关分块"这两件事在数学上不能同时成立——排序器再准也只是下界估计（池化标注下 Recall 是 lower bound，TREC 的通行做法是放宽截断深度或用 condensed list 口径，而不是把未标注当成 0 还要求 85%）。这不是检索链路的问题，是验收指标与标注口径互相矛盾。

**处理（2026-09-26 拍板并落地）**：把门改成 **Recall@10 ≥ 0.85**（上界 0.9469，可达），Recall@5 降为观测项继续报告；Precision@5 / MRR / NDCG@10 三条原值不动。选"看多深"而不是"算多严"，是因为分母只算 grade=2 会让 grade=1 的部分相关彻底不参与评分，第三部分的置信阈值校准反而失去依据。方案 8.1 表格已同步改为 Recall@10。

处理方式：门先不放宽，`TARGETS` 保持方案原值，宁可显示 `targets_passed: false`，也不改数字凑通过。要动门需要明确选一种并同步改方案与本表：把 Recall 的截断深度改成 10（上界 0.9469，最省事、口径最标准），或 Recall 只按等级 2（"非常相关"，均值 3.2 条）计算分母。两个选择的代价不同：前者放宽的是"看多深"，后者放宽的是"算多严"，对第三部分置信阈值校准的影响也不同。

## 4. 各模式分数含义与能不能拿来当阈值

2026-09-25 实测（语料外对照 5 条 / 真实 Query 14 条，`top_k=5`，关闭改写与精排）：

| 模式 | 分数含义 | 语料外对照 Top1 | 真实 Query Top1（min/median/max） | Top1 命中相关的 Query |
|---|---|---|---|---|
| semantic | Qdrant Cosine 相似度 | 0.3767 ~ 0.5450（5 条中 4 条有结果） | 0.7955 / 0.8798 / 0.9383 | 14/14 |
| keyword | BM25 稀疏向量原始分（无上界） | 6.1954 ~ 12.0945（5/5 有结果） | 29.9134 / 60.4863 / 87.5553 | 14/14 |
| hybrid | RRF 融合秩分 | 0.0164 ~ 0.0315（5/5 有结果） | 0.0328 / 0.0483 / 0.0492 | 14/14 |
| fuzzy | pg_trgm `word_similarity` | 无命中（0/5） | 0.5385 / 0.7778 / 1.0000 | 7/14 |

由此确定的规则：

1. **不同模式的分数不可跨模式比较，也不共享阈值**。Cosine 在 0~1、BM25 无上界、RRF 是秩倒数和、trigram 是字面相似度，四者量纲和单调性都不同。
2. **hybrid 的 RRF 分数不能当置信度**：对照最高 0.0315 与真实最低 0.0328 只差 4%，任何阈值不是在切"相关/不相关"，而是在切噪声。
3. **"结果非空"不等于"库里有答案"**：keyword/hybrid 对语料外 Query 也会填满 Top5。要做"知识库未覆盖"判定，只有两条可靠路径：
   - semantic 模式按分数下限（本批数据显示 ~0.70 能同时放过 5 条对照并留住 14 条真实 Query）；该下限属于小样本观察值，**必须在池化冻结集上复算并按索引指纹版本化后**才允许写进调用方规则；
   - 或者不看分数，走"检索→`lookup` 取原文→让生成端核验"，核验不过就回答未覆盖。
4. 在服务端给出校准分数之前，`score_calibrated` 恒为 `false`，接口文档与 SDK 都按此声明。上线条件：在冻结集上按 `score_type` 分别给出经验分布 + 阈值，并把它和 `index_fingerprint` 一起版本化（换 Embedding 模型必须重算）。
5. **fuzzy 是抗拼写误差的补充召回，不是通用检索器**：真实 Query 只有 7/14 能在 Top5 给出相关分块，但它对语料外 Query 100% 空返回，是三条召回路里唯一自带"未覆盖"信号的。

## 5. 影子索引与切换门槛

切换是 fail-closed 的，服务端逐条校验，不看界面状态：重建失败文档数为 0、评估记录来自冻结集且四项指标全部达标、评估对应的配置版本与 Collection 与重建目标一致、在线配置未被改动、重建期间知识库修订号未变、无未结束文档任务，并再次校验影子 Collection 的索引身份。任一条不满足就拒绝，不存在"先切了再看看"的口子，也没有跳过评估的回退开关；要退回旧配置，就对旧版本再走一次重建+评估+切换。

进门的指标固定是 **hybrid × 查询改写 + 精排** 这一格（`acceptance_evaluation.py` 的 `gate_variant`），不是四模式里分数最高的一格。原因有实测依据：影子索引用 Qwen3-Embedding-0.6B/1024 维、在线用 8B/4096 维，两次 `--record` 却记录了完全相同的四项指标（Recall@5 0.9071、MRR 0.9939、NDCG@10 0.9477、Precision@5 0.3106）——因为当时取的是"最高分变体"，两边都落在 keyword 上，而 BM25 稀疏向量在两个 Collection 里来自同样的正文与分词器，分数天然一致。用"表现最好的模式"当门，等于允许一次 Embedding 降级只靠词匹配过关；只有混合检索会真实消耗稠密向量，所以门必须只看它。缺这一格时脚本直接拒绝记录（`--modes` 必须含 `hybrid`，默认已含）。

## 6. 复现步骤

```powershell
# 先设环境变量，否则脚本 import app.* 会 ModuleNotFoundError（2026-09-26 实测踩过）
$env:UV_PROJECT_ENVIRONMENT = "G:\Code_Warehouse\KnowForge\.venv"; $env:PYTHONPATH = "backend"; $env:PYTHONIOENCODING = "utf-8"

# 0) 语料全量入库并收敛（幂等，只补没入库的文件）
uv run python scripts/ingest_corpus.py

# 1) 构建/重建评估集：池化 + 分级标注，输出报告与 review CSV
uv run python scripts/build_eval_dataset.py --version 2026-09 --frozen-target 320 --parallel 4

# 2) 人工抽查（改 human_grade 列后另存为 overrides-2026-09.csv，再跑一次第 1 步即可生效）
#    复核文件：data/evaluation/review-frozen-2026-09.csv

# 3) 冻结集真实评估：四模式 × 改写/精排开关，落 data/acceptance/evaluation-<label>.json
uv run python scripts/acceptance_evaluation.py --dataset data/evaluation/frozen-2026-09.jsonl --label online --record
#    模型配额不可用时只跑不碰远程模型的字面路径（能留档，但 --record 会被切换门拒绝）：
uv run python scripts/acceptance_evaluation.py --modes keyword fuzzy --variants literal --label lit-2026-09-26

# 4) 分路径容量实测（一次一个场景，速率阶梯 + 搜索缓存命中率取自 Prometheus）

```

### 7.2 标签链路（方案 8.2）

- 过审门三处统一为 0.7：代码默认值 `LLM_ONLY_CONFIDENCE`（字段用 `le=` 钉住，写高了 `Settings` 校验就抛错）、回填迁移 `5f1c7be0a9d4`、历史修复迁移 `a3d9c51e7b48`（库里被写成 0.9 的行已改回，实测 `runtime_configurations` 8 行 / `index_rebuilds` 3 行 / `processing_tasks` 69 行全为 0.7）。
- 覆盖率 **0.8549（2132/2494，只数已过审）**，目标 0.95；差的 362 块只挂着"降门之前被判 pending"的老标签行，要靠 `scripts/promote_tags.py` 一次性过审 —— 而它在准确率过 0.85 之前会自己拒绝执行。
- Payload 一致性：**改为全量比对后归零**。此前 `check_payload` 用 `order_by(func.random())` 抽 200 个，两轮报出"2/200""3/200"根本不可比；全量比对查到 **22 个分块 / 3 篇文档**"库里有 approved、payload 是空"，全是 0.9 门那段历史留下的（当时判成 pending，同步推的是空标签，修门后没人再推）。处置走产品自己的路径：`enqueue_catalog_sync` + `dispatch` 三个 `sync_payload` 任务，之后全量比对 0 不一致。
- 准确率 **0.7083（85/120）**，未达 0.85 门。本轮由代理按同一份 rubric 逐行复核（复核看的是 `text_with_context` 前 300 字，与判官同源），与模型判定不同处 9~10 条：把 `并发与多线程`（Dubbo 集群策略表）、`数据去重`（缓存穿透段）、`系统设计题`（生产者-消费者）、`HTTP协议`（Servlet/序列化段）、`性能优化`（fetch 重试段）、`核心功能`（无区分度）判成 bad，把 `SpringMvc`、`localStorage`、`防重复提交`、`浏览器通信` 从 bad 翻回 ok（段落标题就是该技术点，只是正文被表格切碎）。**复核结论不等于人工背书**：`verdict_by` 随判定一起记账，报告里 `verdicts_by_author={agent:qoder: 120}`、`human_verdicts_applied=0`，门额外要求人手判定 `>=100`（`MIN_HUMAN_VERDICTS`），所以只有机器复核时这条门必然不过 —— 这是设计意图，不是 bug。
- 抽样口径已修成稳定的：`stable_tag_sample` 先保留 `data/acceptance/tag-accuracy-sample.json` 清单里仍在库的关联，缺口按 `sha256(seed|chunk_id|tag)` 补 —— 上一版 `random.sample` 只要总体增减一条就整批重抽，把 4 条人工背书静默作废过。报告新增 `sample_fingerprint`（本轮 `0e14b98cec6c53bf`）、`carried_over_from_previous_sample: 120`、`human_verdicts_stale: 0`，填了但对不上样本的判定会显式报数。

易错点：

- worker 停摆不再是静默故障：七个派发点都先过消费侧探测（`celery inspect().ping()`，或"有 120 秒内更新过的 running 任务/重建"这条兜底 —— solo 池的 worker 跑长任务时答不了 ping，只按 ping 判活会把健康的忙 worker 挡掉），拿不到证据就 `409 暂无可用 Worker…`，且在落盘与建行之前拒绝。响应体里已经没有 `queued` 字段：200 就等于"已入队且确认有消费者"。存活状态看 `knowforge_queue_consumer_online`，重建积压年龄看 `knowforge_oldest_pending_rebuild_seconds`（`deploy/monitoring/alerts.yml` 各有关联告警）。注意 Beat 的 `knowforge.recover` 自己也是排在同一个队列上的任务，worker 死了它同样不会跑，所以重建这条链没有自愈，只能重投。
- 容量脚本的 `cached` 场景定义是"命中缓存、不碰模型"。预热只灌 `keyword` 一种模式时，另外三种模式必然 miss 并打到远程模型，测出来的 p95 就不是命中路径的 p95。现在预热按模式统计失败数（`cache_warm_up.failed_by_mode`），只把成功灌满的模式交给 k6；一个都没有则该档记 `skipped` 并给出原因，而不是把 miss 当 hit 报告。
- 评估脚本会创建临时 API Key，跑完必须 revoke（脚本在 `finally` 里做）；残留 Key 会持续吃掉配额。池化一轮可跑一小时以上，管理端 Token 在此之前会过期，所以撤销前必须重新登录取新 Token（2026-09-26 就是因为复用旧 Header 拿到 401，漏下一把 active Key）。
- 后台执行长任务时不要用 `| tail` 收尾，管道会把退出码洗成 0，崩溃也会显示"成功"；改成重定向到日志文件。
- 池化标注依赖在线 Collection 的当前状态；先重建索引再重跑第 1 步，否则 `grades-*.jsonl` 缓存会因 revision 变化整体失效并重算。
