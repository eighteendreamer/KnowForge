# KnowForge 运行与恢复手册

> 适用版本：V1.0 工程实现（本地单机 + 远程模型 API）。所有命令在仓库根目录执行。

## 1. 组件与端口

| 组件 | 位置 | 端口 | 说明 |
|---|---|---|---|
| FastAPI 管理端与开放 API | 本机 `.venv` | 8000 | `app.main:create_app`，含 `/metrics`、`/health` |
| Celery Worker + Beat | 本机 `.venv` | — | 文档入库、元数据同步、删除、索引重建；Beat 每 30 秒补投未收敛任务 |
| 管理后台前端 | Vite | 5173 | 代理 `/v1` 与 `/health` 到 8000 |
| 用户门户前端 | Vite | 5174 | 同样代理 `/v1` 与 `/health` 到 8000；后端没有 CORSMiddleware，两个前端都只能走同源代理，不做跨域直连 |
| PostgreSQL 16 | 容器 `bigdata-major` | 5432 | 元数据事实源，需 `pg_trgm` 扩展 |
| Redis 7 | 容器 `bigdata-major` | 6379 | 队列、限流、检索缓存、模型配额 |
| Qdrant | 容器 `knowforge-qdrant` | 6333/6334 | Dense + BM25 Sparse 向量索引 |
| Prometheus / Grafana | 容器 `knowforge-monitoring-*` | 9090 / 3000 | 指标抓取、告警、面板 |

模型（Embedding、Rerank、标签/改写、扫描页识别）全部走 OpenAI 兼容远程接口，不下载权重、不需要 GPU。

## 2. 首次部署

1. 复制 `.env.example` 为 `.env`，填写 `KNOFORGE_DATABASE_URL`、`KNOFORGE_TEST_DATABASE_URL`、`KNOFORGE_JWT_SECRET`、`KNOFORGE_MODEL_API_BASE_URL`、`KNOFORGE_MODEL_API_KEY`。密钥只允许存在于 `.env` 或密钥管理系统。
2. `.\scripts\setup.ps1` 安装依赖与前端包。
3. `uv run alembic -c backend/alembic.ini upgrade head` 建表（含 `pg_trgm` 扩展与运行配置表）。
4. `uv run python scripts/seed_admin.py` 生成管理员，凭据写入 `data/admin-credentials.txt`。
5. `uv run python scripts/download_tokenizer.py` 拉取分词器词表，索引指纹依赖其内容。
6. `uv run python scripts/register_index_identity.py` 为已有 Collection 登记索引身份（空库或首次上线也必须跑一次）。
7. `.\scripts\start-monitoring.ps1` 启动 Prometheus 与 Grafana；随后 `.\scripts\dev.ps1` 启动应用，保证 API 读到 `KNOFORGE_METRICS_TOKEN`。

## 3. 日常运行

- 启动：`.\scripts\dev.ps1`（API + Worker + Beat + 管理端 5173 + 门户 5174，日志与共享指标目录在 `data/runtime/<时间戳>`）。
- 停止：应用窗口 Ctrl+C；容器用 `.\scripts\stop.ps1`（不动数据卷，不动 `bigdata-major`）。
- 全量检查：`.\scripts\check.ps1`（Ruff、格式、mypy、后端 pytest、迁移漂移、前端 lint/测试/构建）。
- 监控：Grafana `http://127.0.0.1:3000`，面板 `KnowForge · 服务与模型`；Prometheus `http://127.0.0.1:9090`，`/metrics` 需 Bearer Token。

## 4. 配置变更规则

- 运行配置存在数据库 `runtime_configurations`，`runtime_state` 指向当前生效版本；改配置走管理后台“系统设置”或 `PUT /v1/admin/system/settings`，需要超级管理员。
- 每次变更生成新版本行，不原地覆盖；正在执行的文档任务继续使用其提交时的快照，可完整重放。
- 只有不影响向量空间的字段可以直接改（模型超时、重试、并发、RPM、Rerank/标签/视觉模型名、精排开关、缓存 TTL、上传与 PDF 限制、Embedding 批量）。API Key、JWT 密钥、数据库口令仍只读环境变量，绝不入库。
- Embedding 模型、维度、分块参数、分词器决定索引身份（`index_fingerprint`）。这些字段不能直接改，只能“全量重建 → 冻结评估 → 成对切换”。

### 4.1 支付渠道凭据与加密主密钥

- 渠道凭据（支付宝应用私钥、微信商户 API 私钥、APIv3 密钥、Stripe Secret Key 等）在管理后台“充值系统 → 支付渠道 → 完善配置”填写，按厂商字段分别加密后存 `recharge_channel_credentials`；列表只显示 SHA-256 指纹前 12 位、版本号与设置时间，明文永不回显、不进审计与日志。
- 加密主密钥 `KNOFORGE_PAYMENT_MASTER_KEY`（32 字节随机数的 64 位十六进制，生成：`python -c "import secrets;print(secrets.token_hex(32))"`）**只能放 `.env`**。它一旦丢失，已存凭据永久不可读，只能在商户后台重置后重新录入；它与数据库备份必须分开存放（口令管理器/打印），不要把 `.env` 和 `data/backup/` 放进同一个压缩包或同一块盘。
- 升级顺序：先在 `.env` 写好主密钥 → `alembic upgrade head`（迁移 `b5c7e2f4a913` 会把旧的明文 `merchant_id`/`secret` 加密回填并删除那两列，缺主密钥时迁移直接失败而不是降级）→ 起服务。没配主密钥时凭据相关接口一律返回 `503/5003`，其余功能不受影响。
- 配好后必须点行内“自检”：支付宝打一次 `alipay.trade.query`（返回 `40004 交易不存在` 即证明签名与授权有效），微信调 `GET /v3/certificates` 拉取并用 APIv3 密钥解密平台证书，Stripe 打 `GET /v1/balance`。自检结果区分 `live`（真调过厂商）与 `local_only`（只做了本地校验），徽章只认前者。
- 微信回调地址必须是公网可达的 **https** 域名（http 隧道会被拒），域名还需 ICP 备案；`KNOFORGE_SITE_URL` 是回调与跳转地址的拼接基址，改成公网地址后要在厂商后台同步核对。

## 5. 全量重建与受控切换

1. 系统设置页点“全量重建索引”，填目标模型与维度。接口会真实调用一次 Embedding 探测返回维度，维度不符直接拒绝。探测用的是账号的 Embedding 配额：如果同时在跑评估标注这类高频模型调用，这里会直接返回 `429 超过调用频率或日配额限制`，等前一批跑完再点，不要并行抢配额。
2. Worker 在影子 Collection 重嵌入全部分块，在线检索与在线 Collection 不受影响；进度见 `index_rebuilds`，断点记录 `checkpoint_document_id`。
3. 重建完成后状态为 `evaluating`。跑 `uv run python scripts/acceptance_evaluation.py --dataset data/evaluation/frozen-2026-09.jsonl --label shadow --direct auto --record` 记录该索引版本的评估结果。`--direct auto` 会自动取这条未完成重建的目标配置并核对 Collection；不带 `--direct` 的 "shadow" 打的其实是在线 Collection，会留下一份张冠李戴的报告。
4. 点“切换”：服务端在同一事务里校验失败文档数为 0、评估来自冻结集且达标、评估对应的 Collection 与重建目标一致、在线配置未被改动、重建期间知识库修订号未变、无未结束文档任务，并再次校验影子 Collection 的索引身份，最后原子地把查询模型与 Collection 成对切换。
5. 任一条件不满足都会返回明确原因，绝不部分切换。切换后检索缓存键含新配置版本，旧缓存自然失效。

## 6. 故障恢复

| 现象 | 判定 | 处置 |
|---|---|---|
| 在线检索普遍要 1.4 秒 | 单机 2494 分块实测：keyword 默认 1424ms，关掉精排（`options.rerank=false`）91ms，semantic 关精排 352ms | 远程精排是每次检索的主开销。批量导入/评估这类离线任务要关精排或错峰跑；在线对延迟敏感就让调用方显式传 `rerank:false`，或在系统设置里关掉 `rerank_enabled` |
| 提交任务被拒：`暂无可用 Worker：任务队列没有被消费` | `GET /metrics` 的 `knowforge_queue_consumer_online` 为 0 | 七类提交（上传/改文档/重试/删除/重建/重建重试/标签批量变更）都会先探消费者再落盘建行，所以这条 409 是保护而不是故障：起 worker（`scripts/dev.ps1` 会一起拉起 api/worker/beat），确认 `celery@... ready` 后重投即可。判活有两条路：worker 应答 ping，或有 120 秒内更新过的 `running` 任务/重建（solo 池跑长任务时答不了 ping，属正常） |
| 文档卡在 `pending` | `GET /v1/admin/tasks` 无进展，Grafana“最早待处理任务等待”上升 | 先看 `knowforge_queue_consumer_online`：为 0 说明 worker 没在消费，Beat 的补投任务本身也排在同一个死队列上，不会自愈；为 1 才按 Redis/数据库方向查，也可在任务页点“重试” |
| 模型超时（`模型服务调用失败（timeout）`） | `/metrics` 中 `knowforge_model_requests_total{outcome="timeout"}` 上升 | 系统设置里调大 `model_timeout_seconds`、调小 `embedding_batch_size`，再重试失败文档 |
| 模型 429 / 配额等待 | `knowforge_model_quota_wait_seconds`、`KnowForgeModelRateLimited` 告警 | 调低 `model_max_concurrency` 与 `model_requests_per_minute`，等待队列收敛 |
| 扫描页识别失败 | 文档 `parse_error` 记录“页面渲染尺寸超过限制” | 调大 `pdf_max_pixels` 后重试；仍失败则人工处理该文档，不得当空白页通过 |
| API 或 Worker 重启 | 任务表存在 `running` 超过 5 分钟 | Beat 会补投；文档级 advisory 锁保证同一文档串行，不会重复入库 |
| 向量与库不一致 | 检索结果与文档状态不符 | 对单个文档点“重新索引”即可幂等重建其分块与向量 |
| 审核后标签在检索里筛不到 | `acceptance_quality.py`（默认全量比对 payload）报 `tag_payload_mismatches` | 库里有已过审标签、Qdrant payload 的 `tags` 里没有，就是那篇文档的 `sync_payload` 从没在这些关联之后跑过。2026-09-26 实测到 22 个分块（3 篇文档），全部是过审门被错写成 0.9 那段历史时期留下的：标签当时按 0.9 判成 pending，同步推的是空标签，修门之后没人再推一次。处置不是改数据，而是给受影响文档补一次同步：`enqueue_catalog_sync` + `dispatch`（worker 在线时几秒完成），跑完再全量比对应为 0 |
| 带过滤的检索返回 0 | 去掉 `filters` 重跑同一条查询，对比 `total` | `filters.tags` 与 `filters.category` 匹配不到都是空结果而不是报错：标签必须在 `GET /v1/knowledge/tags` 里（只返回已过审），分类路径必须与 `GET /v1/knowledge/categories` 完全一致；两者都对得上且去掉过滤仍为空，才是知识库未覆盖。门户检索试用页因此只让这两个过滤项从这两个接口取值 |
| 一个慢接口拖死全站 | 日志出现 `QueuePool limit ... reached`，`/health` 与文档列表一起变慢 | 检索在远程模型调用前用 `session.commit()` 结束只读事务，不占连接；按容量调 `KNOFORGE_DB_POOL_SIZE`/`KNOFORGE_DB_MAX_OVERFLOW`/`KNOFORGE_DB_POOL_TIMEOUT`，用 `scripts/acceptance_concurrency.py` 复现验证 |
| 影子重建停在 `pending` 不动 | `index_rebuilds.updated_at` 不变，`completed_documents` 为 0；`knowforge_oldest_pending_rebuild_seconds` 上升并触发 `KnowForgeRebuildNotConsumed` | 重建这条链没有自愈路径（Beat 的 `knowforge.recover` 只补投文档任务），起 worker 后点“重试”从断点继续 |
| 影子重建失败 | `index_rebuilds.status=failed` | 修复原因后点“重试”，从断点继续；未通过评估前不可能切换 |
| 需要回退 | 已切换后发现效果劣化 | 在系统设置里对旧配置版本重新走一次“重建 + 评估 + 切换”，不存在跳过评估的回退开关 |

## 6.4 实测容量与 SLO（方案 8.4，2026-09-26，单节点）

同一台机器上跑 API + PostgreSQL + Redis + Qdrant，语料 31 篇 / 2494 分块，k6 每档 30 秒，速率阶梯逐档加压。下表只含**不发起远程模型调用**的三条路径；完整 hybrid 链路要等模型配额恢复后用 `--with-model` 补测，报告里它是 `measured: false`，不要当成 0。

| 路径 | 可持续速率 | 该档延迟 | 首个失败速率 | 失败时的表现 |
|---|---|---|---|---|
| 缓存命中检索 | 60 req/s | p50 44ms / p95 62ms / p99 120ms，命中率 1.0，0 错误 | 120 req/s | 36% 请求 500，p95 10.9s |
| 元数据接口（分类树 + 开放接口清单） | 50 req/s | p50 22.8ms / p95 29.1ms / p99 38ms，0 错误 | 100 req/s | 1.1% 请求 500，p95 4.08s |
| 冷查询，不启用改写与精排（keyword/fuzzy） | 40 req/s | p50 1.57s / p95 2.80s / p99 3.44s，0 错误 | 阶梯内未失败 | — |

权威数据在 `data/acceptance/load-report.json`，分档原始行在 `data/evaluation/load-2026-09-26-final.log`（默认池的对照行在 `load-2026-09-26.log` 与 `load-report-pool-30.json`）。

**上表是实测调出来的连接池，不是猜的。** 代码默认 `KNOFORGE_DB_POOL_SIZE=10` + `KNOFORGE_DB_MAX_OVERFLOW=20`（上限 30 连接、`pool_timeout=5s`）时同样这三条路径是：cached 60 req/s 但 p95 642.8ms / p99 949.2ms、metadata 可持续 50（p99 400ms）而到 150 才失败、cold 只能 20 req/s（50 时 p95 7.1s）。一轮 120 req/s 的阶梯在后端留下 782 条 `QueuePool limit ... reached` / `TimeoutError`，也就是连接池先耗尽而不是 CPU 打满。把上限调到 20+40=60（这台 PG `max_connections=1000`，实测并发连接只有 12，余量充足）之后：cached@60 的 p95 从 643ms 降到 62ms，cold 的可持续速率从 20 翻倍到 40 req/s 且 0 错误，metadata@50 不受影响。该配置已写进 `.env` 与 `.env.example`。剩下的失败边界（cached 120、metadata 100）不再由连接池决定：命中率仍是 1.0，请求是在单个 uvicorn 进程的事件循环上排队，要再往上只能加 API 副本数（方案 6.2 的多副本形态）。

两个必须一起读的口径：① `cached` 场景的定义是命中缓存、不碰模型，所以脚本会先按四种模式各灌一遍，**灌失败的模式不会进入压测**（报告里 `cache_warm_up.failed_by_mode` 记下 semantic/hybrid 各 40 次失败，即模型 402）；② 压测 Key 的限流提到 100000 次/分钟，否则量到的是这把 Key 的 100 req/s 配额而不是节点容量。

### 6.5 批量入库吞吐（方案 8.4 第四行，CPU 段实测）

`uv run python scripts/acceptance_ingest.py --parse-throughput` 直接对整库真实语料跑"解析 + 分块"两段（与入库用的是同一套 `parse_pdf` / `parse_html` / `Chunker`），2026-09-26 本机结果：

| 指标 | 实测 |
|---|---|
| 语料 | 29 个文件（2 个整篇扫描，60 页，见下） |
| 解析出正文的页 | 620 页（其中 10 页是混排文档里的低质量扫描页） |
| 产出分块 | 2228 块 |
| 耗时 | 26.9 秒 |
| 页/分钟 · Chunk/分钟 · 文档/分钟 | 1384 · 4973 · 60.3 |
| 失败率 | 0（2 个整篇扫描文档单独计数，不算失败） |

那 2 个整篇扫描的文档在本机解析不出正文，靠 Qwen3-VL 逐页识别入库（`test_parser.py:142-148` 断言这两篇的识别页数等于总页数，232 个分块全部来自 VL 链路）。向量化、打标、扫描页识别三段的耗时与模型用量同样由模型配额决定，CPU 段远不是瓶颈；注意 `vl_recognizer.py:56-58` 识别成功后会清空识别页列表，AST 里没有"哪几页是 VL 出来的"这一留痕，方案 8.2 要求的记录识别页目前只能从日志还原。原始数据：`data/acceptance/ingest-throughput.json`。

结论：入库的 CPU 段不是瓶颈（一万多页的量级在分钟级），**整条入库链路的上限由模型调用决定**，扩并发之前先看配额。

## 7. 备份与恢复

### 7.1 一条命令备份

```powershell
.\scripts\backup.ps1                      # 默认写到 data\backup\<时间戳>\
.\scripts\backup.ps1 -SkipQdrant          # 语料未变、只想要库与文件时
```

产物与成功标志：

| 文件 | 内容 | 校验方式 |
|---|---|---|
| `knowforge-<时间戳>.dump` | `pg_dump -Fc` 整库（PostgreSQL 在 `bigdata-major` 容器内，脚本用容器里的 `pg_dump` 18.6 走 127.0.0.1） | `manifest.json` 里 `alembic_head` 与 `uv run alembic heads` 一致 |
| `storage-<时间戳>.zip` | `data/storage` 全量（原始文件与 AST） | `manifest.json` 的 `storage_files` 与备份目录内条目数一致 |
| `tech_knowledge_base-<...>.snapshot` | Qdrant Collection 快照（`POST /collections/{name}/snapshots`，含 checksum） | `manifest.json` 的 `points_count` 与 `GET /collections/tech_knowledge_base` 一致 |
| `manifest.json` | 时间、迁移版本、库名、集合名、点数、文件名 | 恢复脚本读它 |

备份目录属于生成物，不入库；异地存放时整套（含 `manifest.json`）一起搬。

`pg_dump` 覆盖的是**已加密**的渠道凭据，所以备份本身不会泄露密钥；但也因此备份里没有解开它们的东西——`KNOFORGE_PAYMENT_MASTER_KEY` 必须由 `.env` 单独备份（口令管理器或打印件），**不要**和备份包放在一起，否则"库备份 + 主密钥"同处就等于把所有商户密钥交出去。

### 7.2 恢复

```powershell
.\scripts\restore.ps1 -Path data\backup\20260926-015506            # 会弹确认
.\scripts\restore.ps1 -Path data\backup\20260926-015506 -WhatIf    # 只看会做什么
```

顺序与要点：

1. 先停 `scripts/dev.ps1`：8000 端口还在监听时脚本直接拒绝执行，避免应用与 `pg_restore` 抢写。
2. 确认目标机的 `.env` 已有 `KNOFORGE_PAYMENT_MASTER_KEY`，且与备份来源环境是同一把：不是同一把时渠道凭据全部解不开，充值页会显示"未配置/自检失败"，只能在商户后台重置后重录。
3. PostgreSQL：`pg_restore -c --if-exists` 覆盖到 `KNOFORGE_DATABASE_URL` 指向的库。恢复后必须再跑一次 `alembic upgrade head`（脚本已做），版本不齐不要启动应用。
4. `data/storage`：解包覆盖，键名是内容无关的 uuid，多余的旧文件不影响已恢复的记录。
5. 向量库：本环境的 Qdrant 版本没有开放 Collection 快照恢复接口（实测 `POST /collections/{name}/snapshots/{file}/recover` 与 `/snapshots/recover` 均 404），快照只用于跨机搬运与留档。向量是可推导数据：库与文件恢复后走第 5 节的“全量重建 → 冻结评估 → 成对切换”重建索引。
6. Redis：允许清空，检索缓存与限流桶会自动重建；清空 Celery 队列后由 Beat 补投未收敛任务。
6. 起应用后先查 `/health`，再用一个已知问题跑检索；两者都正常才算恢复完成。

只验证某个备份能不能用：把 dump 恢复到临时库（如 `knowforge_restore_probe`）比对表数与文档数，再 `DROP DATABASE`，不要碰生产库。

## 7.3 与方案 6.2 的偏差（已确认）

方案 6.2 的 compose 里含 postgres/redis/backend/worker。本机按“Python 用本地 uv 管理”的要求落地为：

- `deploy/docker-compose.dev.yaml` 只保留 Qdrant（镜像按 digest 固定）；PostgreSQL 与 Redis 复用 `bigdata-major` 容器（5432/6379 已发布到 127.0.0.1，`pg_trgm` 装在该容器内）。
- FastAPI、Worker、Beat 由 `scripts/dev.ps1` 用根目录 `.venv` 直接起，日志与共享运行目录在 `data/runtime/<时间戳>/`。
- 因此 compose 里的 `DB_HOST: postgres` 等主机名不生效，连接串一律来自 `.env` 的 `KNOFORGE_*`；迁移与验收脚本同样在宿主机上跑。
- 要回到方案形态（容器内跑后端），需要把 `.env` 换成服务名主机名并保证 Worker 与后端共享同一份存储挂载，其余代码不用改。

前端托管同样是本机形态与方案形态并存：本机由 Vite 起（管理端 5173、门户 5174，两者的 `vite.config.ts` 都把 `/v1` 与 `/health` 同源代理到 8000）；方案里的"Nginx 静态托管 + 反向代理 API"给了模板 `deploy/nginx/knowforge.conf.example` 与 `deploy/nginx/knowforge-api-proxy.conf`。模板只到"能照抄"的程度——本机没有 nginx，未做过 `nginx -t` 与真实转发验证，上线时按站点实际情况改 `server_name`/`root` 后再验。两个前端都不能跨域直连：后端没有 CORSMiddleware，同源代理是硬约束而不是偏好。`/metrics` 不进反代，它只给 Prometheus 抓。

后台项与方案 4.2 的两处有意差异：

- “存储路径配置”在系统设置里只读：`storage_path` 参与运行配置快照但不允许在线改，改了会让已入库文档的 `source_path` 集体失效。要换盘按“停应用 → 迁目录 → 改 `.env` → 起应用”的顺序走，属于运维动作而不是配置项。
- “LLM 配置（API 地址）”里模型名可在线改（`llm_model`），但 `model_api_base_url` 属于索引身份字段：换地址等于换一套向量空间，只能通过“全量重建 → 冻结评估 → 成对切换”生效，避免在线混存两套模型的向量。
