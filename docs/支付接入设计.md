# 支付接入设计

充值系统怎么收渠道凭据、怎么验密钥、还差什么才能真收款。这份文档只描述当前状态与既定路线，不记流水账。

## 1. 数据模型

| 表 | 作用 | 关键约束 |
|---|---|---|
| `recharge_channels` | 渠道骨架：`code`（不可改，账本按它引用）、`display_name`、`channel_type`、`enabled` | `channel_type IN ('alipay','wechat','stripe','custom')` |
| `recharge_channel_credentials` | 一个凭据字段一行：`ciphertext BYTEA`、`key_version`、`fingerprint`、`secret_class`、`set_by_id` | `UNIQUE(channel_id, key_name)`、`key_version >= 1`、随渠道 CASCADE |
| `recharge_packages` | 金额档位 | `amount_cent > 0`、`bonus_cent >= 0` |
| `balance_transactions` | 余额唯一事实来源（余额=SUM，不落列） | `amount_cent > 0`，本轮无冲正/退款 |

早期版本渠道表只有 `merchant_id String(200)` + 一列**明文** `secret Text`：微信 APIv3 要 5 项、支付宝证书模式要 3 证 + 私钥 + 3 个序列号，一个槽位装不下，所以管理端表单只能长成两个字段。迁移 `b5c7e2f4a913` 把旧值加密回填成 `legacy_secret` / `legacy_merchant_id`（能过类型校验的商户号回填成正规键），然后把明文列删掉。

## 2. 字段规格与表单

`backend/app/services/payments/specs.py::CREDENTIAL_SPECS` 是唯一事实源，管理端通过 `GET /v1/admin/recharge/credential-specs` 拿字段清单渲染表单，前端不复制字段名与提示文案（同 AGENTS 里"过滤项必须来自服务端元数据"的理由）。

- **支付宝**（12 项）：`app_id`、`gateway_url`（只给正式/沙箱两个枚举值，不让人手输）、`app_private_key`、`alipay_public_key`、`notify_url`、`return_url`、`sign_type`（固定 RSA2，只读）、`charset`（固定 UTF-8，只读）、证书模式三证、`content_encrypt_key`。证书序列号 `app_cert_sn`/`alipay_cert_sn`/`alipay_root_cert_sn` 由服务端解析证书算出，不要求人手填。
- **微信**（9 项，APIv3 普通商户直连）：`mch_id`、`app_id`、`apiv3_key`（恰好 32 字节）、`merchant_private_key`、`cert_serial_no`、`notify_url`（**强制 https**）、`wechat_pay_public_key` + `wechat_pay_public_key_id`、`platform_cert`。平台证书不需要人工提供：自检调 `GET /v3/certificates`，用 APIv3 密钥解密后回存。
- **Stripe**（6 项）：`secret_key`、`webhook_signing_secret`、`publishable_key`、`api_version`、`success_url`、`cancel_url`。环境不另设字段——密钥前缀就是事实。
- **custom**：0 项，给线下对公之类不可在线下单的渠道。

私钥/公钥同时接受控制台给的**裸 base64** 与 PEM 两种形态，入库前统一规范化成 PEM。

## 3. 加密与读写契约

- `KNOFORGE_PAYMENT_MASTER_KEY`（`.env`，32 字节 hex）→ `HKDF-SHA256(salt=channel_id, info="knowforge-payment:{key_name}:{key_version}")` → AES-256-GCM，AAD = `channel_id|key_name|key_version`。跨渠道搬密文、用旧版本冒充新值都解不开。
- 主密钥缺失时凭据读写一律 `503/5003` 并指名环境变量，不降级成明文。
- 列表接口对密钥类凭据**连解密都不做**，只回显指纹（`sha256(明文)[:12]`）、版本与设置时间；非密钥项（商户号、AppID、回调地址）回显原文，否则运营无法确认配的是哪个环境。
- PATCH 三态：键缺省=保留、有值=轮换（`key_version+1`）、`null`/空串=清除；值没变就不写、不涨版本。旧版把 `secret` 总是带在 body 里，改个显示名就会静默清空密钥，这条契约连同测试把它堵死（`test_payment_credentials.py`、`frontend/src/tests/recharge.spec.ts`）。
- 审计只记改动的字段名（`credentials.app_private_key` 这种），值永不进审计表。

## 4. 连通性自检

`POST /v1/admin/recharge/channels/{id}/verify` 返回 `{mode, passed, checks[]}`，`mode` 只允许 `live`（真调过厂商）或 `local_only`。

| 厂商 | 权威检查 | 判通过的信号 |
|---|---|---|
| 支付宝 | 对不存在的单号发一把签好名的 `alipay.trade.query` | `code=40004`（含 `ACQ.TRADE_NOT_EXIST`）——签名被网关受理且应用有效，不产生任何交易 |
| 微信 | `GET /v3/certificates` | 200 且能用 APIv3 密钥解密出平台证书；响应用刚取回的证书验签（引导信任） |
| Stripe | `GET /v1/balance` + Bearer | 200 |

区分得出来的错误类别才有用：`isv.insufficient-isv-permissions` 报成"应用未获得该接口权限，需完成产品签约或授权"，而不是含糊的"密钥无效"。RSA/AES 全部走 `asyncio.to_thread`，事件循环心跳由测试盯着。

## 5. 入账路径现状

目前唯一入账路径仍是 `POST /v1/admin/users/{id}/recharge`（`channel="manual"`）。渠道配置完整只是"能下单"的前提，不代表已经在收钱。

## 6. 还差什么（WP2 / WP3）

1. **下单与回调**：`payment_orders`（`out_trade_no` UNIQUE 作幂等锚点，`provider_trade_no` 只建普通索引）、状态机 `created→pending→(paid|expired|failed)` 且允许 `expired→paid`（本轮没有冲正能力，扫码慢一步的钱必须还能入）、`POST /v1/portal/orders`、`POST /v1/payments/notify/{wechat|alipay|stripe}`（无鉴权、必须消费原始字节/原始表单字段，应答分别是 `{"code":"SUCCESS"}`、纯文本 `success`、`200`）。入账唯一入口用 CAS `UPDATE ... WHERE status IN ('pending','expired') RETURNING id`，且**入账前核对回调金额与订单金额**。
2. **主动查单入账优先于回调**：微信回调要求公网 https，本地隧道给不出，所以查单入账（`alipay.trade.query` / `GET /v3/pay/transactions/out-trade-no/{no}` / Stripe retrieve）要随下单一起落地，回调只是把延迟从轮询周期降到秒级。
3. **对账**：`beat_schedule` 加 `payments.expire`（60s）与 `payments.reconcile`（5min），`task_queue._worker_is_busy` 改成 `(model, predicate)` 对才能识别 `pending` 订单。
4. **门户**：档位/渠道选择 → 立即支付 → 微信二维码、支付宝与 Stripe 跳转 → 轮询入账。现有测试 `portal-pages.spec.ts` 里"不提供下单按钮"的承诺要按"无可付渠道时不提供"改写。
5. 本轮明确不做：退款与负向流水、跨币种换汇、服务商/ISV、APP 与 JSAPI 支付、微信证书自动轮换。

## 7. 已验证与未验证

已验证：迁移在开发库与 `knowforge_test` 上跑通，旧 `wx` 行按预期变成"待配置·已停用·带两个历史键"；凭据 CRUD、三态轮换、启用闸门、缺主密钥 fail-closed、级联删除；支付宝自检**真实打到正式网关**（用假 AppID 得到 `40002 isv.invalid-app-id` 并被正确判为未通过）；管理端 1440×900 实测弹窗 720px、字段与提示来自服务端、密钥只显指纹。

未验证：微信真机联调（需要真实商户凭据 + 公网 https 回调）、支付宝正式环境下单（当前只验到签名与授权这一层）、Stripe（尚未配置测试密钥）、以及任何"扫码付款→自动到账"的端到端闭环。
