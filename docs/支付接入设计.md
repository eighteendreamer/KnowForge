# 支付接入设计

充值系统怎么收渠道凭据、怎么验密钥、还差什么才能真收款。这份文档只描述当前状态与既定路线，不记流水账。

## 1. 数据模型

| 表 | 作用 | 关键约束 |
|---|---|---|
| `recharge_channels` | 渠道骨架：`code`（不可改，账本按它引用）、`display_name`、`channel_type`、`enabled` | `channel_type IN ('alipay','wechat','stripe','custom')` |
| `recharge_channel_credentials` | 一个凭据字段一行：`ciphertext BYTEA`、`key_version`、`fingerprint`、`secret_class`、`set_by_id` | `UNIQUE(channel_id, key_name)`、`key_version >= 1`、随渠道 CASCADE |
| `recharge_packages` | 金额档位 | `amount_cent > 0`、`bonus_cent >= 0` |
| `balance_transactions` | 余额唯一事实来源（余额=SUM，不落列） | `amount_cent > 0`，本轮无冲正/退款；`payment_order_id` 指回订单，人工入账留空 |
| `payment_orders` | 在线下单：金额与赠送在下单时冻结成快照 | `out_trade_no` UNIQUE（幂等锚点）、`status IN ('created','pending','paid','expired','failed')`、`(status, expires_at)` 索引给关单与对账扫 |
| `payment_order_events` | 订单时间线（产品视图，不与审计表混用） | `detail JSONB` 只放摘要与白名单标量，原始回调报文与密钥永不进这里 |

早期版本渠道表只有 `merchant_id String(200)` + 一列**明文** `secret Text`：微信 APIv3 要 5 项、支付宝证书模式要 3 证 + 私钥 + 3 个序列号，一个槽位装不下，所以管理端表单只能长成两个字段。迁移 `b5c7e2f4a913` 把旧值加密回填成 `legacy_secret` / `legacy_merchant_id`（能过类型校验的商户号回填成正规键），然后把明文列删掉。

## 2. 字段规格与表单

`backend/app/services/payments/specs.py::CREDENTIAL_SPECS` 是唯一事实源，管理端通过 `GET /v1/admin/recharge/credential-specs` 拿字段清单渲染表单，前端不复制字段名与提示文案（同 AGENTS 里"过滤项必须来自服务端元数据"的理由）。

- **支付宝**（12 项）：`app_id`、`gateway_url`（只给正式/沙箱两个枚举值，不让人手输）、`app_private_key`、`alipay_public_key`、`notify_url`、`return_url`、`sign_type`（固定 RSA2，只读）、`charset`（固定 UTF-8，只读）、证书模式三证、`content_encrypt_key`。证书序列号 `app_cert_sn`/`alipay_cert_sn`/`alipay_root_cert_sn` 由服务端解析证书算出，不要求人手填。
- **微信**（9 项，APIv3 普通商户直连）：`mch_id`、`app_id`、`apiv3_key`（恰好 32 字节）、`merchant_private_key`、`cert_serial_no`、`notify_url`（**强制 https**）、`wechat_pay_public_key` + `wechat_pay_public_key_id`、`platform_cert`。平台证书不需要人工提供：自检调 `GET /v3/certificates`，用 APIv3 密钥解密后回存。
- **Stripe**（6 项）：`secret_key`、`webhook_signing_secret`、`publishable_key`、`api_version`、`success_url`、`cancel_url`。环境不另设字段——密钥前缀就是事实。
- **custom**：0 项，给线下对公之类不可在线下单的渠道。

私钥/公钥同时接受控制台给的**裸 base64** 与 PEM 两种形态，入库前统一规范化成 PEM。

## 3. 加密与读写契约

- `KNOFORGE_PAYMENT_MASTER_KEY`（`.env`，32 字节 hex）→ `HKDF-SHA256(salt=channel_id, info="knowforge-payment:{key_name}:{key_version}")` → AES-256-GCM，AAD = `channel_id|key_name|key_version`。跨渠道搬密文、用旧版本冒充新值都解不开。
- 主密钥缺失时凭据读写一律 `503/5003` 并指名环境变量，不降级成明文。
- 列表接口对密钥类凭据**连解密都不做**，只回显指纹（`sha256(明文)[:12]`）、版本与设置时间；非密钥项（商户号、AppID、回调地址）回显原文，否则运营无法确认配的是哪个环境。
- PATCH 三态：键缺省=保留、有值=轮换（`key_version+1`）、`null`/空串=清除；值没变就不写、不涨版本。旧版把 `secret` 总是带在 body 里，改个显示名就会静默清空密钥，这条契约连同测试把它堵死（`test_payment_credentials.py`、`frontend/src/tests/recharge.spec.ts`）。
- 审计只记改动的字段名（`credentials.app_private_key` 这种），值永不进审计表。

## 4. 连通性自检

`POST /v1/admin/recharge/channels/{id}/verify` 返回 `{mode, passed, checks[]}`，`mode` 只允许 `live`（真调过厂商）或 `local_only`。

| 厂商 | 权威检查 | 判通过的信号 |
|---|---|---|
| 支付宝 | 对不存在的单号发一把签好名的 `alipay.trade.query` | `code=40004`（含 `ACQ.TRADE_NOT_EXIST`）——签名被网关受理且应用有效，不产生任何交易 |
| 微信 | `GET /v3/certificates` | 200 且能用 APIv3 密钥解密出平台证书；响应用刚取回的证书验签（引导信任） |
| Stripe | `GET /v1/balance` + Bearer | 200 |

区分得出来的错误类别才有用：`isv.insufficient-isv-permissions` 报成"应用未获得该接口权限，需完成产品签约或授权"，而不是含糊的"密钥无效"。RSA/AES 全部走 `asyncio.to_thread`，事件循环心跳由测试盯着。

自检结论**持久化在渠道行上**（`verified_at` / `verify_passed` / `verify_detail`，迁移 `d8a3f1c65027`），列表徽章因此能区分"配置完整但未自检"与"自检未通过 + 原因"。改动任何一项凭据会把这三列清空——换过密钥之后上一次的"通过"不作数。


## 5. 入账路径

在线入账只有一个写法：`backend/app/services/payments/settlement.py::mark_paid_and_credit`。
它先 `SELECT ... FOR UPDATE` 锁住订单行读回当前状态，只有还没 `paid` 的那一次才允许往
`balance_transactions` 追加流水并把订单翻成 `paid`，因此回调重投、门户轮询查单、对账补单同时到达也只入一次账。
余额按流水汇总、没有读改写，所以不需要锁账号行，串行语义全在订单这一行的锁上。

三条路径都汇到这一个入口：

| 路径 | 入口 | 用途 |
|---|---|---|
| 厂商回调 | `POST /v1/payments/notify/{code}`（无鉴权，消费原始字节/原始表单字段） | 秒级到账；应答按厂商各自要求：支付宝纯文本 `success`、微信 HTTP 200 + JSON、Stripe HTTP 200 |
| 门户主动查单 | `POST /v1/portal/orders/{out_trade_no}/sync` | 回调进不来时（本地没有公网 https）唯一能常态工作的入账路径，弹窗每 10 秒自动走一次 |
| 定时对账 | celery beat `knowforge.reconcile_orders`（60s） | 关到期单前先问一次厂商，把"第 29 分钟才付成功"的钱补回来 |

人工入账仍是 `POST /v1/admin/users/{id}/recharge`，账本里 `payment_order_id` 为空——"这笔钱是谁确认收到的"永远可查。

**入账前必须核对金额**：厂商回执的实收金额与订单快照不一致时一分钱不记，写一条 `amount_mismatch` 事件挂起，
管理端「充值订单 → 待人工核对」能筛出来。被挂起的单不再进对账扫描，否则对账会变成无限重试。
状态机是 `created→pending→(paid|expired|failed)`，且**允许 `expired/failed→paid`**：本轮没有冲正能力，
扫码慢一步或本地先超时的钱必须还能入账。

## 6. 还差什么

WP1（凭据与自检）、WP2（下单/回调/查单/入账/门户界面）、WP3（对账与管理端台账）都已落地。剩下的：

1. **支付宝证书模式下单**：`verification_key()` 已能从「支付宝公钥证书」抽公钥做响应与回调验签，
   但下单还缺 `app_cert_sn` / `alipay_root_cert_sn` 两个公共参数（需按 OpenSSL DN 串取 MD5），未取证前不硬编。
   用户若确认应用走证书模式，这块要补。
2. **Stripe 联调**：适配器与 webhook 验签已实现并有测试，但没有真实密钥跑过下单。
3. 本轮明确不做：退款与负向流水、跨币种换汇、服务商/ISV、APP 与 JSAPI 支付、微信平台证书自动轮换。

计划里原本还有一条"把 `task_queue._worker_is_busy` 改成 `(model, predicate)` 对以识别 pending 订单"，
**实际不需要**：下单在请求内同步完成，对账由 beat 直接调度 `knowforge.reconcile_orders`，
两条路都不经过 `require_consumer` 那道消费门，没有需要被识别成"有活干"的 pending 订单。

## 7. 已验证与未验证

**已用真实商户凭据在本机跑过（凭据只加密存进本地库，不进仓库）：**

- 微信 `wechat-native`：自检 `mode=live` 全项通过——商户 API 私钥可解析（RSA-2048）、`GET /v3/certificates` 真取回 1 张平台证书、并用该证书验过响应签名（证书序列号 `3F5B4A0D…`）。商户号、证书序列号、私钥、APIv3 密钥四件套确认互相匹配且可用。
- 支付宝 `alipay-web`：请求侧通过——正式网关受理了签名并回 `40004 ACQ.TRADE_NOT_EXIST`，证明应用私钥与 AppID 正确、应用可调 `alipay.trade.query`。响应验签未通过：三种候选待签串（节点原文 / 带 `"节点":` 前缀 / 整个响应体）都验不过配置里那把"支付宝公钥"，且它不等于应用私钥自带的公钥，因此判定为该字段本身不对（拷成了别处的值，或应用实际走公钥证书模式）。列表徽章如实显示"自检未通过 + 原因"。
- 门户下单真机走通（本地 dev 库 + 正式网关配置）：选档位→立即支付→弹窗出带签名的 `alipay.trade.page.pay` 跳转地址、商户单号与倒计时；点「我已完成支付」触发主动查单，真打到正式网关并把厂商自己的结论 `code=40004 交易不存在` 如实显示在弹窗里。下单只产地址、不发请求，所以这一步不会在厂商侧留下交易。

**其余已验证**：迁移在开发库与 `knowforge_test` 上跑通，旧 `wx` 行按预期变成"待配置·已停用·带两个历史键"；凭据 CRUD、三态轮换、启用闸门、缺主密钥 fail-closed、级联删除、改凭据后自检结论作废；管理端 1440×900 实测完善配置弹窗 720px、字段与提示来自服务端、密钥只显指纹；三家下单/查单/回调验签适配层、入账幂等与金额闸门、对账关单、两端界面各有组件测试覆盖；全量门禁 `scripts/check.ps1` 绿（后端 336 例、覆盖率 80%、无 schema 漂移、管理端 38 例、门户 52 例）。

**仍未验证**：真实付款→自动到账的闭环（没人真付过钱，所以入账依赖的"已验签的成功回执"只在测试桩里出现过）；
支付宝在响应验签修好之前的**查单入账**——`query_order` 只认验过的响应，验不过就按未付处理，这是设计而不是缺陷；
微信 Native 下单会真的在商户侧生成预下单，本轮刻意没跑；Stripe 无密钥；微信回调落地（需公网 https 域名，当时隧道是 http）。
